# 平台守门人整改报告

统一平台重大事项、整改承诺、验证证据和监管报告，落实平台在**数据、算法、流量和规则**方面的守门人责任。

## 业务事实

- 监管将综合运用标准、价格执法和质量监管整治内卷式竞争
- 平台企业需要承担数据、算法、流量和规则管理责任
- 垄断风险监测与经营者集中审查需要技术支撑

## 协作角色

- 市场监管人员
- 平台企业（合规负责人、各整改团队）
- 经营商家
- 案件审查人员

## 服务能力（`src/reporting.py`）

一次重大事项不再由各团队分别报送、难以核对，而是进入统一服务：

1. **分级报送**：重大 / 较大 / 一般三级，按等级自动设定初报时限（重大 2 小时、较大 24 小时、一般 3 天），并可核查初报是否按期。
2. **跨团队归并**：同一事件的多团队上报按“影响时间窗 + 规则/算法版本 + 共有信号词”自动归并到同一事项（如一次算法回滚同时关联商家申诉、价格补贴、流量歧视三份上报）。规则版本必须精确一致，不同版本不会误并。
3. **事件冻结**：事件发生后冻结影响时间窗、规则/算法版本、受影响主体、临时措施；冻结后任何更正都走修订留痕，原始内容不被覆盖。
4. **分派整改**：根因调查、用户补救、制度修订、复测四条工作线分派到团队；**复测必须在根因调查与制度修订审签通过后才能提交证据**。
5. **整改承诺与期限提醒**：每条工作线登记承诺内容、责任团队与截止时间，自动生成逾期 / 临近到期（3 天）提醒。
6. **证据审签**：证据提交人与审签人职责分离（不得自审）；审签驳回使行动项重开，重新提交后再审；含商业秘密的证据必须登记受控存放位置与授权名单。
7. **商业秘密受控附件**：原文留在受控位置，对外（含监管组合视图）只提供脱敏视图，未授权审签人无法审签受控证据。
8. **复发关联**：本次事件与既往同类事件双向关联，便于判断是否反复发生。
9. **自动监测只提线索**：监测系统只能登记“待核实”线索，**必须经人工核实采纳后才能建立事件**；被否决的线索不产生任何事项。
10. **监管摘要防淡化**：存在未解决风险时，摘要必须明示风险（驳回、逾期、整改中、待复测等），“已全面解决”式表述会被拒绝。
11. **承诺对照与关闭门禁**：监管人员可逐条比较平台承诺与实际完成（是否兑现、是否按期）；四条工作线全部审签通过、完成不晚于承诺、且已有监管摘要，事件方可关闭。

## 目录说明

- `contracts/domain.schema.json`：共享领域资料的字段与基本约束。
- `contracts/reporting.schema.json`：报告服务快照（事件、线索、冻结修订、工作流、承诺、证据审签）的束约。
- `fixtures/context.json`：不含真实个人信息的公开领域样例。
- `fixtures/build_incident_fixture.py`：用服务 API 构建活动样例的脚本。
- `fixtures/incidents.json`：由脚本生成的活动样例（3 个事件、3 条线索，纯虚构数据）。
- `src/records.py`：领域资料读取与基础校验。
- `src/reporting.py`：重大事项与整改报告服务核心。
- `tests/`：资料读取测试与报告服务测试（48 个用例）。

## 活动样例走读（`fixtures/incidents.json`）

- **INC-0001（历史，已关闭）**：上半年流量分配歧视事件，四条整改线全部审签通过，作为复发关联的既往事件。
- **LEAD-0001**：算法运行监测平台发现异常，但**只形成线索**；合规值班经理人工采纳后才建立 INC-0002。另有一条监测线索经人工核实为大促正常波动，未采纳、未立案。
- **INC-0002（重大，整改中）**：排序模型回滚同时引发商家申诉失败、补贴错发、流量歧视。算法、商家治理、流量三团队上报归并为同一事件；冻结后发生两次版本补充与两次事实更正，均留痕；根因调查已按期审签通过，用户补救证据（含商业秘密，受控附件）审签被驳回且承诺逾期，制度修订临近到期，复测因前置未完成无法提交；与 INC-0001 建立复发关联；监管摘要如实列明未解决风险。
- **INC-0003（较大，整改中）**：数据接口字段越权，根因已通过，用户补救证据待审，展示另一分级与状态。
- **LEAD-0003**：截至样例时点仍待人工核实，系统从未自动立案。

监管人员通过 `regulator_view` 可一次看到：冻结信息与修订留痕、归并来源团队、未解决风险、逐条承诺与实际完成对照、脱敏后的证据材料。

